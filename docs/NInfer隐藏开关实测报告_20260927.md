# NInfer 隐藏加速开关实测报告（bonsai27b @ RTX 3080 Laptop 16GB）

日期：2026-09-27 晚 | 引擎：master-build 自编译版（发布包不认 t2_g128_fp16）
模型：Ternary-Bonsai-2-27B-ninfer-v3 | 服务参数基线：`--spec dflash2 --draft-tokens 7`
负载：P1 重复型 256 tok 生成 / P2 普通问答 256 tok / 7.6K token 预填充
质量探针：greedy 温度 0 下 P2 输出文本 MD5 一致性

## 二、逐项结论

1. **解码端已经到顶**。四个无损开关（lookup/mlp-a8/cublas 及其组合空间）对解码速度的影响全部在 ±1% 噪声带内（119.5 vs 118.9~119.4）。引擎的解码路径（三值 LUT 内核 + dflash2 投机 + CUDA graphs）没有留下可白捡的余量。
2. **lookup-ngram 8 本次未复现 +16%**。原因清楚：本次 P1 生成的是"逐行重复同一句"，第 8 行之后 n-gram 全命中、前 8 行靠 dflash2，与上次"复读 12 遍长句"的场景不同。上次结论不变：**重复密集型内容（照抄/改写/模板填充）加 lookup 有 16% 级增益，普通内容零拖累**——它是唯一值得日常挂着开的开关。
3. **kv-dtype k8v4 双重否决**：慢 8%（144.2/115.8）且 greedy 输出改变（MD5 不一致）。bonsai 的 KV 本来就是 4 层里 3 层线性注意力、已极省，再压只亏不赚。
4. **prefill-cublas 无差**：预填充瓶颈不在此（7.6K prompt 冷启动 5.4s≈1400 tok/s，二三次命中前缀缓存后 <0.1s）。日常聊天预填充根本不是瓶颈。
5. **mtp-experts-q4 不适用**：官方报错说明它只作用于 MoE MTP 层，bonsai 是稠密模型。

## 三、论文扫描（2026-09 arXiv）

- 动态树投机（EAGLE-3 系）在温度>0 时有一hot塌缩问题，新论文在解 stochastic 场景——对贪心解码的我们无影响，但说明草稿模型研究仍活跃。
- BitNet 硬件类论文（CGLA/int4 指令单元等）全是专用硬件方向，Ampere 消费卡无关。
- FastMTP 类递归草稿头：需要引擎支持，同 EAGLE 一样卡在"改引擎"前置。

## 四、最终口径（可对外）

- **普通生成 ~120 tok/s，重复密集内容 +lookup-ngram 可到 ~160**，全部无损（MD5 级验证）。
- 解码端压榨空间已被引擎吃完；要再快只剩改引擎接更强草稿（EAGLE 类，2-3× 理论空间，以周计的项目）。
- 显存端无新增动作：weights 7.99 GiB + KV，16GB 卡无压力。

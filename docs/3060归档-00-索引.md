## 一、结论速览（先看这个）

| 项目 | 结果 |
|---|---|
| **最终 decode 速度** | **108.7 t/s**（HTTP 三轮回合中位；服务端日志交叉一致） |
| 稳态区间 | ~105 t/s ±5%，无随时间漂移 |
| **prefill 速度** | 640 t/s |
| 接受率 | **96.2%**（608/632） |
| 相对无投机基线 17.5 t/s | **6.21×** |
| 相对最初 MTP d4 的 64.0 t/s | **+70%** |
| 距带宽折算目标 ~173 t/s | 63%（残差归因 28 SM 并行度上限 + sm_86 无 FP8 张量核） |
| 正确性 | 金标准 3/3；输出与基座模型**逐字节相同** |
| 源码改动 | **最终调优阶段未改一行源码**（只换了投机后端 + kv-capacity 口径） |

**最终配置**（已落盘为 `启动脚本/start-8099-sm86.bat`）：

```
bonsai2_27b_ternary_v2-dflash2.ninfer
  --max-context 24576 --kv-capacity 24576 --kv-dtype int8
  --max-concurrency 1 --no-thinking --greedy
  --spec dflash2 --draft-tokens 7 --lm-head-draft
```

**一句话机理**：MTP 的草稿头逐 token 串行（每草稿 token 约 +5 ms/轮）；DFlash2 把 K 个草稿一趟并行出
（K=5→7 每轮只涨 2 ms）。所以 DFlash2 K=7 拿到 7.77 tok/轮而只花 74 ms —— 这是快 47% 的全部原因。

## 五、七个坑（都踩过，别再踩）

| # | 坑 | 症状 | 处理 |
|---|---|---|---|
| 1 | **`-j 24` 并行编译** | 内存（31.8 GB）被 ~2 GB/编译单元吃爆 → 内核 BugCheck + 死机 | 降到 **`-j 6`**；本次 398/398 零错误 |
| 2 | **CUDA 12.8 不认 VS 18** | `host_config.h:170 fatal error C1189` | 换 **CUDA 13.3** |
| 3 | **sm_86 没有 FP8 张量核** | 12 个 FP8-mma 单元 ptxas fatal | 排除 + `src/ops/fp8_a8_stubs.cpp` 替代（运行时明确报错） |
| 4 | **缺 UCRT / FFmpeg dll** | 启动即 `0xC0000135` | 从 Windows SDK Redist 复制 46 个 UCRT dll；从原包 `engine/` 复制 7 个 FFmpeg dll |
| 5 | **dflash2 + `--kv-capacity auto`** | 12 GB 卡直接**拒启**（auto 强制多留 1 GiB headroom） | 改**显式容量**；`--lm-head-draft` 是 dflash2 强制项，不加启动即崩 |
| 6 | **系统设了 `http_proxy`** | 请求 localhost 被送进代理 → 502，看着像服务端崩了 | 基准/curl 一律加 `NO_PROXY=127.0.0.1,localhost` |
| 7 | **短输出伪造"低接受率"** | 收尾句请求接受率只有 35.9%，长输出是 96.2% | **日志 `output` 短于 ~400 token 的样本一律丢弃**；别再把它当成卡的属性 |

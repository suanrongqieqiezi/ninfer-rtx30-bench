# NInfer 自编译打通记录（franken/v0.11 → RTX 3080 Laptop 16GB）

## 结论
编译路线完全打通。此前"源码编译是死路"的结论是误判，真实死因是编译器版本用错。

## 前因后果（完整链条）
1. **旧死因翻案**：9-25 的编译失败日志（E:\AI\build.log）显示，nvcc 因宿主编译器太老把 `-std=c++20` **静默降级**为 C++17，导致 `std::span` 等语法在 device.h 炸出 100 错。当时记录成"CUDA 12.8 拒绝 C++20"是错的——CUDA 12.8 本身支持，需要 MSVC ≥19.30（VS2022）。
2. **VS2022 已在本机**：`E:\AI\VS2022BuildTools`（MSVC 14.44.35207，_MSC_VER 1944）是 9-25 会话装好的，微软签名可验。烟测 `smoke20.cu`（std::span + kernel）一次通过。
3. **依赖**：FFmpeg 用会话遗留 shim（`E:\AI\cmake-modules\FindFFMPEG.cmake`）指向 `C:\FFmpeg`；curl 用 anaconda 的 8.1.1（`-DCURL_LIBRARY=...libcurl.lib -DCURL_INCLUDE_DIR=...`）。
4. **全量编译**：719 步 ninja 全过，产物 `build-ninja\apps\{ninfer,ninfer-serve,ninfer-perplexity}.exe`（各 ~470MB，静态链 CUDA）。
5. **启动撞上 SM 数问题**：BF16 GDN gating 的调度路由表按 RTX 3090 的 **82 SM** 驻留上限设计（`kMinSupportedSmCount=82`，表注释写明 246 CTA 上限）；本机 3080 Laptop 只有 **30 SM**（90 CTA），cooperative 内核预检全部不合法，且选路器先于回退直接抛异常。

## 两处补丁（src/ops/gdn_gating_proj/bf16/bf16_gdn_gating_proj_plan.cpp，原件备份 .orig3090）
- **补丁1**：`bf16_gdn_gating_resolve_plan` 两条路由循环加 `candidate_is_legal(route.schedule, problem)` —— 选路时跳过本机驻留不合法的候选。
- **补丁2**：循环落空时不再抛 "no covering route"，回退到对任何合法问题都成立的 `MmaUnsplit`（表内它本就负责 3457+ 任意列）。

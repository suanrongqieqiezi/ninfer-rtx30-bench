# Ternary-Bonsai-2-27B × NInfer · RTX 30 系真机实测

> 面向：手上有 RTX 30 系（sm_86）或 40 系（sm_89）显卡、想跑这个三值 27B 模型的人
> 定位：原作者在文档里公开标了「30 系真机性能未知 ❌ / 这一步只有你能做」，这里就是那份作业
> 硬件：RTX 3080 Laptop 16GB（本机实测）＋ RTX 3060 12GB（归档实测）

---

## 先说结论

| 卡 | 显存 | decode | prefill | 说明 |
|---|---|---|---|---|
| **RTX 3080 Laptop** | 16 GB | **108.5 / ~120 / 145–165 t/s**（见下表） | 1520 t/s | DFlash2 K=7，三档口径 |
| **RTX 3060** | 12 GB | **108.7 t/s** | 640 t/s | DFlash2 K=7，接受率 96.2% |
| RTX 40/50 系 | — | 可跑，靠 PTX JIT | — | 首次启动多等 1–2 分钟，吃不到原生 SASS |

两张卡速度几乎一样（108.5 vs 108.7），不是巧合——**这个模型的 decode 基本被显存带宽锁死，而 3060 和 3080L 的带宽量级接近**。真正的差别在 prefill（3080L 是 3060 的 2.4 倍）和能开多大上下文。

**同一张 3080 Laptop 的 decode 有三个口径，别互相替代：**

| 工况 | decode | 说明 |
|---|---|---|
| 3.5K 长上下文 + DFlash2 K=7 | **108.5 t/s** | 上表那一格用的就是它，验收率 29.6% |
| 256 token 短生成 · 普通问答 | **~120 t/s** | 日常聊天更接近这一档 |
| 256 token 短生成 · 重复密集内容 + `--lookup-ngram 8` | **145–165 t/s** | 复读 / 照抄 / 模板类内容；位级无损 |

> 常被引用的 **"160" 出自第三档**——它是重复密集内容的成绩，既不是普通问答，也不是长上下文成绩。

## 一、30 系为什么被落下

NInfer 官方构建脚本把 CUDA 目标写死成 `sm_120a`（RTX 5090），显式拒绝其他架构。原作者发布的两个包（极速档 PQ2 / 均衡档 PTQ1）里，引擎只带两个二进制：

- `ninfer-serve.exe` → **sm_89**（RTX 40）
- `ninfer-serve-sm120.exe` → **sm_120a**（RTX 50）

**没有 86。** 而且两份二进制各自只含自己架构的机器码，**都不带对方架构的 PTX**。CUDA 机器码不向下兼容，也没有 PTX 可回退——拿错不是"慢一点"，是**没有任何可用内核镜像（表现为卡死）**。

所以 30 系（含 3060 / 3070 / 3080 / 3090，全部 sm_86）用不了现成引擎，只能自己从源码编。

---

## 二、怎么编出 sm_86 引擎

原作者其实把方法写在文档里了（`适配案例集` 案例 2/3），我们照着做并补了真机踩到的坑。核心是三处改动：

| # | 改什么 | 落点 |
|---|---|---|
| 1 | 放行架构门 | `CMakeLists.txt` 架构白名单加 `86`，`NINFER_SM_COUNT` 加 86→SM 数分支 |
| 2 | 补宏 | 加 `NINFER_SM86=1`（代码里已有分支在等） |
| 3 | 按 shared 预算重调内核 | 超 48 KiB 静态 shared 的 `.cu` 排除或换 4-warp 变体 |

**关于 48 KiB 静态 shared 硬墙**（案例 3，我们验证一致）：sm_86 和 sm_89 的静态 shared 上限相同（48 KiB），不是"30 系更宽松"。实测 `ptxas` 报 `0xc200 > 0xc000`（49,664 B > 49,152 B）就是这个墙。动态 shared 走 opt-in 通道，上限 101,376 B——本机 3080L 实测就是这个数（和 40 系包里的 `gpu-probe.exe` 结论一致）。

### 我们真机踩到、说明文档没提的坑

| # | 坑 | 症状 | 处理 |
|---|---|---|---|
| 1 | **`-j 24` 并行编译** | 31.8 GB 内存被模板重的 CUDA 单元（单进程峰值 1.5–3 GB）吃爆 → 内核 BugCheck + **整机死机** | 降到 **`-j 6`**，398/398 零错误 |
| 2 | **工具链版本两头堵** | 3060 线：CUDA 12.8 **不认** VS 18/MSVC 19.51（`host_config.h:170 C1189`）→ 换 **CUDA 13.3**；本机线：编译器**太老**，`-std=c++20` 被静默降级成 C++17 → 换 VS2022 | 各自换到匹配的版本 |
| 3 | **sm_86 没有 FP8 张量核** | 12 个 FP8-mma 单元 `ptxas` fatal | 排除 + `src/ops/fp8_a8_stubs.cpp` 替代（16 个 FP8 入口实现为运行时明确报错） |
| 4 | **缺 UCRT / FFmpeg dll** | 启动即 `0xC0000135` | 从 Windows SDK Redist 补 45–46 个 UCRT dll；从原包 `engine\` 复制 7 个 FFmpeg dll |
| 5 | **12 GB 卡：`--kv-capacity auto` 会让 dflash2 拒启** | 报 `minimum Engine runtime reservation requires 1,414,716,672 bytes ... only 2,028,002,816 available` | 改**显式容量**（去掉 auto 强制的 1 GiB headroom）；`--lm-head-draft` 是 dflash2 强制项，不加启动即崩 |
| 6 | **系统设了 `http_proxy`** | localhost 请求被送进代理 → 502，看着像服务端崩了 | 基准/curl 一律加 `NO_PROXY=127.0.0.1,localhost` |
| 7 | **短输出伪造"低接受率"** | 收尾句接受率只有 35.9%，长输出是 96.2% | 日志 output 短于 ~400 token 的样本一律丢弃 |

> 坑 5 的**口径警告**：`--kv-capacity` 显式值**只在 12 GB 卡上是对的**。16 GB+ 的卡应当保留 `auto`。别把这条抄到别的卡上。

## 三、30 系真机实测数据

### RTX 3080 Laptop 16GB

| 配置 | 解码速度 | 备注 |
|---|---|---|
| NInfer + DFlash2 K=7 | **108.5 tok/s** | 3.5K 上下文，验收率 29.6% |
| NInfer dense（关投机） | 49.8 tok/s | — |
| llama.cpp（同权重转 Q8_0） | 35.7 tok/s | 官方 fork |
| + `--lookup-ngram 8`（重复密集内容） | **145–165 tok/s** | 输出位级无损 |

prefill：3.5K 上下文约 **1520 tok/s**。

> **数字口径说明**：上表 108.5 来自 3.5K 长上下文场景；另有一组短生成实测（256 token）为普通问答 ~120、重复密集内容加 `--lookup-ngram 8` 达 145–165。**"160"这个数出自后者**——它是重复密集内容（复读/照抄/模板类）的成绩，不是普通问答。引擎的解码路径（三值 LUT + dflash2 + CUDA graphs）已无便宜可捡——四个无损开关（lookup / mlp-a8 / prefill-cublas / kv-dtype）实测全在 ±1% 噪声带内。

### RTX 3060 12GB

| 项 | 结果 |
|---|---|
| decode | **108.7 t/s**（HTTP 三轮回合中位，服务端日志交叉一致） |
| 稳态区间 | ~105 t/s ±5%，无时间漂移 |
| prefill | 640 t/s |
| 接受率 | 96.2%（608/632），按位置 `90,90,89,88,84,84,84` |
| 相对无投机基线 17.5 t/s | **6.21×** |
| 正确性 | 金标准 3/3；输出与基座模型**逐字节相同** |

**关键机理**（为什么 DFlash2 比 MTP 快一倍）：MTP 的草稿头**逐 token 串行**推进（每草稿 token 约 +5 ms/轮）；DFlash2 把 K 个草稿**一趟并行**出（K=5→7 每轮只涨 2 ms）。所以 DFlash2 K=7 拿到 7.77 tok/轮而只花 74 ms。**K≤7 是硬上界**（K=8 起单轮成本跳 3 倍），104~109 t/s 就是这条路的终点。

## 四、40 / 50 系能用吗

**能，但走的是 PTX 前向 JIT，不是原生机器码。**

我们自编译的 `ninfer-serve.exe` 里，我实测扫过二进制：**内嵌 384 个 `.target sm_86` 的 PTX 段，0 个 sm_89 / sm_120 的 SASS**。

- sm_89（40 系）/ sm_120（50 系）的驱动可以**把 sm_86 的 PTX 即时编译**（JIT）成自己架构的机器码——所以能跑；
- 代价：**首次启动多等 1–2 分钟**（驱动在 JIT），只慢这一次；
- 但**吃不到 Ada / Blackwell 的原生指令**（比如 FP8 张量核），性能不会是这两代卡的上限。

一句话：40 系用这份构建能跑、且是目前少有的现成 Windows 选择，但它**不是为 40 系优化的**；追求 40 系极限应自己去编 sm_89 目标。

## 五、给你的复现路径

```
# 1. 启动（3080L 16G 口径，保留 auto）
ninfer-serve.exe Ternary-Bonsai-2-27B-ninfer-v3.ninfer ^
  --host 127.0.0.1 --port 8905 --model-id bonsai-27b ^
  --max-context 8192 --kv-dtype rk8v4 --gdn-state-fp16 ^
  --spec dflash2 --draft-tokens 7

# 12G 卡把上下文容量改成显式（否则拒启）：
#   --max-context 24576 --kv-capacity 24576   ← 去掉 auto

# 2. 验证（注意绕代理）
set NO_PROXY=127.0.0.1,localhost
curl http://127.0.0.1:8905/v1/chat/completions ...
```

**前置**：Windows 10/11 x64；NVIDIA 驱动 ≥ 570（无需装 CUDA Toolkit）；整条路径不要带空格/中文/括号。
